## 1. Краткий вердикт

Проект сейчас сильнее всего на уровне **продуктовой документации** и слабее всего на уровне **исполняемой системы**.

- В `docs/` уже описаны позиционирование, MVP-путь, AI Brain, каталог, партнёры, цены, сценарии и модели данных.
- В `frontend/` есть кликабельный скелет клиентского пути на mock-данных.
- `backend/`, `database/`, `scripts/` — пустые заготовки.
- Настоящего AI, хранения заявок, партнёрской базы и production-пайплайна нет.

Для MVP это нормальный старт **если** приоритет — проверить спрос и получить заявки.  
Для масштабирования текущий разрыв docs ↔ код станет главным риском.

## 2. Архитектура проекта

### 2.1. Задуманная платформенная архитектура (из docs)

Платформа строится **вокруг технологий изготовления**, не вокруг SKU-каталога.

```
Клиент
  ↓
AI Gift Brain / Gift Engine
  (запрос/фото → получатель → повод → стиль → товары → набор)
  ↓
Мокапы + сцена готового подарка
  ↓
База партнёров (технологии / товары / цены / сроки)
  ↓
Производство → контроль качества → доставка → вручение
```

Три слоя экосистемы (`22_Product_Ecosystem.md`):

| Слой | Содержание |
|---|---|
| Клиентский | запрос, визуализация, выбор, заявка |
| AI | идея, стили, мокапы, сборка набора |
| Производственный | технологии, партнёры, цены, сроки |

Ключевое правило: AI никогда не предлагает то, чего нельзя произвести.

### 2.3. Frontend-архитектура (факт)

**Стек:** Next.js 16.2, React 19, TypeScript, Tailwind CSS 4, шрифты Nunito + Unbounded.

**Роутинг (MVP UI):**

```
/            главная (баннер + запрос + категории + «как это работает»)
  ↓ overlay «Подбираем подарки...» (fake delay)
/ideas       варианты (фильтры + mock-карточки)
/product     карточка идеи + trust-блок
/checkout    форма заявки
```

**Слои frontend:**

| Путь | Роль |
|---|---|
| `app/` | страницы App Router |

Нет слоёв `services/`, `api/`, `hooks/` (кроме локальной логики в компонентах), нет state-management, нет auth, нет загрузки фото на сервер.

## 3. Сильные стороны

1. **Ясное позиционирование.** Документы последовательно фиксируют: не магазин кружек, а сервис от идеи до вручения. Это снижает риск «сделать ещё один каталог сувениров».

2. **Архитектурный принцип «технологии → товары → партнёры».** Правильная основа для маркетплейса производства: AI и каталог привязаны к реальной исполнимости.

3. **Глубокая продуктовая проработка.** Есть Vision, User Flow, Customer Journey, AI Brain, Gift Engine, Customizer, Pricing, Corporate, Knowledge Base, экосистема и модели данных.

4. **Knowledge Base как источник истины.** `23_Gift_Knowledge_Base.md` даёт алгоритмический каркас: получатель → повод → интересы → стиль → товар → набор → технология → партнёр.

5. **MVP осознанно урезан.** В `00_Project_Status.md` и Roadmap явно отложены кабинеты партнёров, полная автоматизация, app, сложная CRM. Цель — заявки и проверка спроса.

6. **Frontend уже проводит пользователя по короткому пути.** Есть эмоциональный UI, fake «AI думает», фильтры идей, checkout и success — можно тестировать UX без backend.

7. **Бизнес-логика заявок описана прагматично.** Статусы `lead → contacted → confirmed → assigned → …`, SLA «связаться в рабочий день», финальная цена подтверждается человеком.

8. **Единый визуальный язык frontend.** CSS variables, тёплая палитра, display-шрифт Unbounded — бренд читается.

## 4. Слабые стороны

1. **Разрыв docs ↔ код.** Документация описывает Gift Engine, мокапы «один дизайн — много товаров», наборы, апселлы, статусы заказа. Код показывает emoji-карточки и mock shuffle.

2. **Нет backend и БД.** Заявки не сохраняются, менеджер не уведомляется, фото не хранятся, партнёры не выбираются системно.

3. **«AI» сейчас декоративный.** Overlay и кнопка «Сгенерировать еще» не анализируют запрос. Параметр `q` только отображается.

4. **Дублирование / шум во frontend.**
   - `frontend/ai-gift-marketplace/` — отдельный недоделанный Next-проект (Pages + App смесь).
   - Неиспользуемые `category-cards.tsx`, `popular-gifts.tsx`.
   - Пустая папка `gift-wizard/`.
   - Риск путаницы «какой frontend настоящий».

5. **Несогласованность экранов с MVP-спекой.**
   - На product нет дополнений (упаковка/открытка/апселлы).
   - Нет сцены «один дизайн на нескольких товарах».
   - Checkout шире минимальной заявки из docs (адрес/доставка/фиктивные суммы без реальной калькуляции).
   - Ideas ближе к каталогу карточек, чем к «готовым сценам подарков».

6. **Пустые/недописанные документы.** `06_Pricing.md`, `07_Competitors.md`, `09_Ideas.md`, `10_Decisions.md`, `17_User_Flow.md` — заглушки. Решения не зафиксированы в Decisions.

7. **Корневой README почти пустой.** Для публичного GitHub это слабый onboarding.

8. **Нет инженерной дисциплины репозитория.** Один коммит, нет CI, нет issue/PR-процесса, нет лицензии, нет env-примера, нет тестов.

9. **Фото-загрузка не функциональна end-to-end.** Имя файла может попасть в state, но файл никуда не уходит и на подбор не влияет.

10. **Ценообразование в UI оторвано от формул.** В docs есть формулы и ориентиры; в mock — фиксированные числа без связи с партнёрским прайсом.

## 6. Задачи до MVP (приоритетный backlog)

Цель MVP из docs: **простой путь → заявки → связь с клиентом → первые заказы вручную**.

### P0 — must have (без этого MVP не проверяет спрос)

1. **Зафиксировать единый frontend.** Оставить App Router в `frontend/`, убрать/архивировать `frontend/ai-gift-marketplace/` и мёртвые компоненты.
2. **Канал приёма заявок.** Минимум: форма → Telegram/email/Notion/Sheet + запись ID. Идеально: простая таблица `leads` + уведомление.
3. **Собрать состав заявки.** В lead должны попадать: контакты, исходный запрос, выбранная идея, флаг фото, комментарий.
4. **Сделать выдачу хоть немного «умной» без LLM.** Rule-based ранжирование по Knowledge Base (брат/мама/жена → релевантные mock-идеи).
5. **Довести product до MVP-минимума.** Основной товар + 2–4 дополнения (упаковка, открытка, шоколад/свеча) + итоговая ориентировочная цена.
6. **Собрать офлайн-базу партнёров Красноярска** (таблица: технология, товары, цена, срок, контакт) — даже вне кода.
7. **Прописать операционный SLA.** Кто отвечает на заявку, в какой мессенджер, что говорить клиенту.
8. **Подтянуть README и деплой.** Как запустить, какой URL, что является MVP-скоупом.

### P1 — should have (сильно повышает конверсию)

9. Реальные изображения/мокапы хотя бы для MVP-товаров (кружка, футболка, холст, магнит, открытка, упаковка).
10. Единый entry-point «генерации» для всех кнопок (промпт, категории, «что заказать»).
11. Упростить checkout до полей из Business Rules (имя, телефон/мессенджер, комментарий).
12. События аналитики: start_search, view_ideas, open_product, submit_lead.
13. Юридический минимум: согласие на обработку контактов.

### P2 — nice for MVP+, не блокирует первые заявки

14. Загрузка фото в storage.
15. Черновой Gift Engine API (без генерации картинок): parse intent → scenarios → products.
16. Простая админка заявок со статусами `lead/contacted/confirmed`.
17. Корпоративная заявка отдельной формой.
18. Заполнить Decisions / Competitors / Pricing stubs.

### Явно не делать до проверки спроса

- Кабинеты партнёров
- Автоназначение заказов
- Полная онлайн-оплата и сложная CRM
- Мобильное приложение
- Масштаб на много городов
- Генерация всех AI-стилей в проде

## 7. Что может помешать масштабированию

1. **Отсутствие данных как продукта.** Если Knowledge Base / сценарии / партнёры останутся только Markdown, масштабировать подбор нельзя — не на чем исполнять правила.

2. **Каталог-мышление в UI.** Если `/ideas` останется сеткой SKU-карточек, продукт скатится в обычный интернет-магазин и потеряет дифференциацию.

3. **Жёсткая связка UI ↔ `MOCK_IDEAS`.** Без слоя домена (GiftIdea, Scenario, PartnerOffer) каждый новый экран будет копипастой; переход на API станет болезненным.

4. **Два frontend в одном дереве.** Удвоит стоимость поддержки и даст ложные PR/деплои.

5. **Ручной контур без системности.** MVP на менеджере ок, но без статусов, SLA и истории заявок команда упрётся в операционный потолок раньше, чем в технический.

6. **Нереалистичные обещания AI.** Если маркетинг обещает «AI создаёт дизайн», а клиент видит emoji и shuffle — доверие и retention падают.

7. **Цена без партнёрского прайса.** Масштаб по городам требует формулы `partner_cost + service + packaging + delivery + margin`. Иначе маржа непредсказуема.

8. **Нет контроля качества как процесса.** В docs качество — ответственность сервиса; без чек-листа приёмки брак партнёров убьёт бренд.

9. **B2B раньше B2C-операционки.** Корпоративные тиражи сложнее (образец, согласование, документы). Ранний уход в B2B без отлаженного personal-flow опасен.

10. **Публичный репозиторий без дисциплины.** Без Issues/PR/CI/секретов сложно растить команду и не ломать MVP.

11. **Перегрузка scope из документации.** Docs описывают экосистему уровня большой платформы. Если воспринимать всё сразу как MVP — скорость упадёт, а спрос так и не проверится.

## 9. Рекомендуемая стратегия (без смены архитектуры)

1. Сохранить продуктовую архитектуру docs: технологии → партнёры → AI-подбор → заявка → ручное исполнение.
2. Не строить «большой backend» до первых заявок.
3. Сделать тонкий исполняемый слой над уже описанными сущностями:
   - rule-based подбор из Knowledge Base / scenarios;
   - lead capture;
   - офлайн-партнёрская таблица.
4. Визуально двигаться от «карточек каталога» к «готовому подарку / набору».
5. Настоящий generative AI и кабинеты партнёров — этап 2, после подтверждённого спроса.

## 11. Итог

AI Gift Marketplace — **хорошо описанный продуктовый замысел** с правильной архитектурой (технологии + партнёры + AI-подбор), и **ранний UI-прототип** без backend/данных/реального подбора.

Главный риск не в отсутствии «ещё одной фичи», а в том, чтобы:

- не расползтись в большую платформу до первых заявок;
- не потерять дифференциацию, скатившись в обычный каталог;
- вовремя превратить Markdown-модели в минимально исполняемые данные и lead-flow.

До MVP достаточно узкого контура: **понятный сайт → релевантные варианты → дополнения → сохранённая заявка → менеджер → ручное производство у партнёра**.
